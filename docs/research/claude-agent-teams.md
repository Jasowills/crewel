# Claude Agent Teams — Primary-Source Research

**Date:** 2026-09-02  
**Scope:** How Claude Agent Teams works per first-party sources (Anthropic docs, Claude Code docs, Anthropic blog/engineering posts, `claude-code` GitHub), and what an OpenCode-native equivalent with multi-agent support would require. Crewel vision is treated as the desired target; current crewel implementation is summarized only for contrast.  
**Method:** Every claim below is tied to the owner source that makes it. Secondary write-ups are not cited unless they quote a primary source verbatim.

---

## 1. What is Claude Agent Teams?

**Official definition:** "Coordinate multiple Claude Code instances working together as a team, with shared tasks, inter-agent messaging, and centralized management." One session acts as _team lead_, coordinating work, assigning tasks, and synthesizing results; teammates work independently, each in its own context window, and communicate directly with each other. The user can also talk to any teammate directly without going through the lead. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams)

**Positioning vs. single-agent Claude Code and other parallelization modes:** Claude Code offers four parallel-work surfaces. The docs explicitly compare them on _who coordinates_ and _whether workers communicate_: [code.claude.com/docs/en/agents](https://code.claude.com/docs/en/agents)

| Approach                     | What it gives you (per docs)                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Subagents                    | Delegated workers inside one session; results return to caller                                                                    |
| Agent View (`claude agents`) | Dispatch/monitor background sessions you hand off                                                                                 |
| **Agent Teams**              | Multiple coordinated sessions with shared task list + inter-agent messaging, managed by a lead; experimental, disabled by default |
| Dynamic Workflows            | Script that runs many subagents and cross-checks results                                                                          |

Agent Teams is the only mode where _Claude_ plans, assigns, and supervises the group; the other modes are either human-coordinated or single-session delegation. [code.claude.com/docs/en/agents](https://code.claude.com/docs/en/agents) · [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Compare with subagents table)

**Launch intent:** Introduced alongside Opus 4.6 as a research preview for tasks that split into independent, read-heavy work (reviews, research, new modules, debugging with competing hypotheses). The Opus 4.6 announcement frames it as: "you can now spin up multiple agents that work in parallel as a team and coordinate autonomously." [anthropic.com/news/claude-opus-4-6](https://www.anthropic.com/news/claude-opus-4-6) · [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) ("When to use agent teams")

**Experimental status (important):** Disabled by default; enable via `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in `settings.json` or environment. Without it, no team directory is written and Claude does not spawn teammates. The docs warn of known limitations around resumption, task coordination, and shutdown. As of v2.1.178, `TeamCreate`/`TeamDelete` tools no longer exist — spawning a teammate no longer needs a setup step and cleanup happens automatically on session exit. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Warning + Enable + Note on v2.1.178)

## 2. How it works under the hood

### Team creation and lead/subagent roles

- **Teams are session-scoped and lead-fixed.** A session has exactly one team scoped to that session; teammates cannot spawn teammates; leadership cannot be transferred. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Limitations: "One team per session", "No nested teams", "Lead is fixed")
- **How Claude starts teams:** Claude launches a teammate when it calls the `Agent` tool with a `name` while agent teams are enabled. Claude may also name ordinary subagents on its own; while the experimental flag is on, a named subagent launches as a teammate. Split-pane `TeamCreate`-style setup was removed in v2.1.178. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (How Claude starts agent teams) · [code.claude.com/docs/en/tools-reference](https://code.claude.com/docs/en/tools-reference) (`Agent` tool description)
- **Roles (Architecture table):** Team lead = main session that spawns/manages; Teammates = separate Claude instances on assigned tasks; Task list = shared work items; Mailbox = messaging system. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Architecture)

### Spawning and context windows

- **Each teammate is a separate Claude Code instance with its own context window.** The docs repeat this for token-cost reasoning and for the subagent-vs-team comparison table: "Own context window; fully independent" vs. subagents' caller-owned summary. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Compare table, Token usage, Context and communication) · [code.claude.com/docs/en/costs](https://code.claude.com/docs/en/costs) (Agent team token costs)
- **What teammates inherit:** Same project context as a regular session — `CLAUDE.md`, MCP servers, skills — plus the spawn prompt. The lead's conversation history does _not_ carry over. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Context and communication)
- **Model per teammate (deterministic order):** (1) model named in spawn prompt, (2) `model` in a referenced subagent definition (`inherit` = lead's model), (3) `CLAUDE_CODE_SUBAGENT_MODEL` env var (when not `inherit`), (4) lead's current model. `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` applies to teammates; `availableModels` allowlist substitution rules apply. Before v2.1.251 the env var was first. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Specify teammates and models) · [code.claude.com/docs/en/sub-agents](https://code.claude.com/docs/en/sub-agents) (Choose a model)
- **Display-mode interaction with subagent definitions:** For in-process teammates, `tools` is limited to definition's list + `SendMessage` + Task tools; `body` appended to system prompt; `mcpServers` ignored. For split-pane teammates, `body` replaces the default prompt and `mcpServers` is applied. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Use subagent definitions for teammates)
- **Interactive-only constraint:** Spawning requires an interactive session; in `claude -p` non-interactive / Agent SDK sessions, named subagents run as ordinary subagents. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Enable agent teams, paragraph on non-interactive mode)
- **Reuse of subagent definitions:** Defining a reusable role once (e.g., `security-reviewer`) and referencing it both as a subagent and as a team teammate is the documented path for role reuse. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Use subagent definitions for teammates)

### Long-running harness vs. product feature

Anthropic's only long-running parallel benchmark (C compiler, ~2,000 sessions, ~$20k) used a _custom external harness_, not the shipped Agent Teams product: a bare git repo + Docker containers per agent, git-based lock files under `current_tasks/`, and an infinite `claude -p` loop. That prototype had no orchestration agent, no mailbox, and no shared task list — it is not the product's architecture, but it shows the problems a product must solve (test-oracle design, dedup, merge-conflict handling). [anthropic.com/engineering/building-c-compiler](https://www.anthropic.com/engineering/building-c-compiler) (Running Claude in parallel; Lessons)

## 3. Coordination mechanism

**Answer: file-based on local disk — plus a JSON mailbox — coordinated through Claude's Team API (Agent + Task + SendMessage tools) and Claude-managed locking.** No in-memory bus; no cloud team service.

- **Task list:** Shared list with states `pending` → `in progress` → `completed`; dependencies supported (pending task with unresolved deps cannot be claimed). Agents _without_ Task tools coordinate through messages instead. Task claiming uses file locking to prevent races. Dependencies are auto-unblocked when a prerequisite completes. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Assign and claim tasks; Architecture: "Claude Code manages task dependencies automatically")
- **Mailbox:** JSON file per agent at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`. Validated on read; malformed entries reported and removed (pre-v2.1.207 blocked delivery). "Sent" means the recipient's file was written successfully; disk-full / permission errors return an error to the sender. Direct peer-to-peer messaging (one message per recipient); automatic delivery and idle notifications to the lead. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Architecture: mailboxes + message-delivery guarantees) · [code.claude.com/docs/en/tools-reference](https://code.claude.com/docs/en/tools-reference) (`SendMessage`, `ListAgents` semantics)
- **Storage locations (session-derived name = `session-` + 8 chars of session ID):** Team config `~/.claude/teams/{team-name}/config.json` (runtime state: session IDs, tmux pane IDs; removed on session exit; do not hand-edit), task list `~/.claude/tasks/{team-name}/` (persists locally, never uploaded; retention governed by `cleanupPeriodDays`). Teammate discovery via `config.json: members[]` (`team-lead` vs. named agent type). Project-level `teams.json` is _not_ a recognized config. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Architecture: Teams and tasks are stored locally; team config members array)
- **Tool surface:** `Agent(name=…)` to spawn, `SendMessage` to send, `TaskCreate`/`TaskGet`/`TaskList`/`TaskUpdate` for the board, `TaskStop`/`Cron*` retained for teammates, plus `ListAgents` to enumerate addressable agents. Availability of Task tools depends on session/model; `TodoWrite` is disabled when Task tools are present unless `CLAUDE_CODE_ENABLE_TASKS=0`. [code.claude.com/docs/en/tools-reference](https://code.claude.com/docs/en/tools-reference) (Agent, SendMessage, TaskCreate/List/Get/Update, TodoWrite) · [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Compare table: "plus a shared task list for agents that have the Task tools")
- **Hooks as coordination gates:** `TeammateIdle` (exit 2 keeps teammate working), `TaskCreated`, `TaskCompleted` — all can block/instruct. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Enforce quality gates with hooks) · [code.claude.com/docs/en/hooks](https://code.claude.com/docs/en/hooks) (Hook lifecycle: `TeammateIdle`, `TaskCreated`, `TaskCompleted`)
- **Cross-session messaging beyond the team:** `SendMessage` and `ListAgents` also reach other local/web sessions; unrelated to the team mailbox but uses the same tool. [code.claude.com/docs/en/tools-reference](https://code.claude.com/docs/en/tools-reference) (`SendMessage`, `ListAgents`) · [code.claude.com/docs/en/agents](https://code.claude.com/docs/en/agents) (Cross-session messaging bullet)
- **Permissions between agents:** Teammates start with the lead's permission mode; permission prompts bubble to the lead. Inter-agent messages are tagged as coming from another Claude session (not the user) and cannot approve prompts or bypass consent; in `auto` mode the classifier treats relayed approvals as untrusted and reviews messages before delivery. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Permissions: Messages between agents, Auto-mode checks)

## 4. UI / UX

- **How the user interacts with lead vs. teammates:** Tell the lead in natural language what you want; it handles decomposition, assignment, and delegation. Message any teammate directly by name to redirect or ask follow-ups; in in-process mode plain text/skills go to the viewed teammate while built-in commands still run in the lead. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Control your agent team; Talk to teammates directly)
- **TUI surface:** Integrated into Claude Code's own terminal. The lead's terminal shows teammates in an _agent panel_ below the prompt (the same panel used for subagents, so panel presence alone doesn't confirm a team). Selection: Up/Down → Enter to open/message; Esc to clear/stop; Ctrl+T toggles task list; `x` stops selected teammate; shutdown via natural language ("Ask the researcher teammate to shut down"). [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Start your first agent team; Talk to teammates directly; Shut down teammates)
- **Display modes:** Two — `in-process` (all teammates inside the main terminal; works in any terminal, no setup) and `split panes` (`tmux` or iTerm2 + `it2` CLI; click into pane for full session). Default is `in-process` since v2.1.179 (was `auto`); `auto` enables split panes when already inside tmux or iTerm2-with-`it2`, else in-process. `teammateMode` in `~/.claude/settings.json` or `claude --teammate-mode auto` controls it. As of v2.1.186, `iterm2` mode is explicit. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Choose a display mode)
- **Visibility mechanics:** As of v2.1.199, idle rows stay while any agent is still working; after all idle, rows hide after 30 s and reappear on next turn; >3 idle rows collapse into `N idle agents`. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Start your first agent team: agent-panel behavior)
- **Plan-before-implement:** Lead in plan mode → spawned teammates are read-only until plan approval; the lead auto-approves the plan when ready (no user prompt) but edits still flow through permission prompts. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Have teammates plan before implementing)
- **No terminal multiplexing beyond tmux/iTerm2:** The product does _not_ ship its own multiplexer; it reuses tmux/iTerm2. Split panes are not supported in VS Code integrated terminal, Windows Terminal, or Ghostty. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Limitations: Split panes require tmux or iTerm2)

## 5. Limitations (per docs + cost page)

From the shipped docs (not speculation):

- **Session resumption:** `/resume` and `/rewind` do not restore in-process teammates; lead may message teammates that no longer exist — spawn new ones. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Limitations)
- **Task status lag:** Teammates sometimes fail to mark tasks completed, blocking dependents; manual nudge or edit may be needed. [ibid.](https://code.claude.com/docs/en/agent-teams)
- **Shutdown latency:** Teammates finish their current request/tool call before shutting down. [ibid.](https://code.claude.com/docs/en/agent-teams)
- **Single-vendor and model-fixed:** Every teammate is a Claude Code instance; vendor is Anthropic only. Teammate model and fast mode are fixed at spawn; `/model` and `/fast` only affect the lead. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Limitations + Talk to teammates directly: model/fast-mode paragraph)
- **Token cost scales linearly with team size; cache asymmetry.** Docs: "Token usage scales with the number of active teammates." Costs page: "Agent teams are disabled by default…"; "Agent teams use significantly more tokens…"; compaction/cache docs note in-process teammates' requests fall _outside_ the main conversation's cache TTL bucket (5 min default; 1 h via `subagentPromptCacheTtl` billed higher). [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Token usage) · [code.claude.com/docs/en/costs](https://code.claude.com/docs/en/costs) (Agent team token costs; Track your costs preamble)
- **File conflicts if boundaries are wrong:** Agent teams do _not_ isolate teammates in git worktrees; docs advise partitioning by file ownership to avoid overwrites. The C-compiler prototype had to invent a GCC-oracle harness to parallelize a single giant target (Linux kernel). [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Best practices: Avoid file conflicts; Choose an appropriate team size) · [anthropic.com/engineering/building-c-compiler](https://www.anthropic.com/engineering/building-c-compiler) (Make parallelism easy)
- **Non-interactive / headless blocked:** `claude -p` and Agent SDK sessions cannot spawn teammates. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Enable agent teams, non-interactive paragraph)
- **Other hardcoded limits:** No nested teams, no `background: true` subagents from in-process teammates, permissions set at spawn (per-teammate modes only after spawn), exactly one team per session. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Limitations)

## 6. What an OpenCode-native equivalent would look like

The goal (per brief) is an OpenCode-native teams implementation — OpenCode as primary, with optional Claude Code / Codex participation on the same board, mirroring Claude Agent Teams' shape but not its vendor lock-in. The spec/PRD calls this "crewel vision." Each mapping below names the Claude concept, the OpenCode concept, and the adapter-level translation needed.

### Concept map: Claude → OpenCode → Crewel vision

- **Lead role:** Claude: main session is fixed lead. OpenCode: any `primary` agent (typically `build` or a custom `lead` agent) can act as lead; primary agents are cycled via Tab / `switch_agent` keybind and invoked via `@`. Crewel vision: dedicated non-coding lead (never writes code) — `docs/PRD.md:38-41`, `docs/DECISIONS.md` — decomposes requests into tickets, assigns, reviews. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Lead is fixed) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Primary agents) · `docs/PRD.md:38-41`
- **Teammate vs. subagent distinction:** Claude: teammates are independent sessions with own context + direct messaging; subagents are single-session delegated workers. OpenCode: `mode: subagent` agents run in child sessions with fresh context; a primary agent invokes them via the `task`/`subagent` tool (foreground or background), and the child uses its own configured permissions/model. Crewel vision: teammates are _not_ OpenCode subagents; they are top-level turn-based workers in isolated git worktrees, each producing a `TurnReport`. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Compare table) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Subagents run in child sessions) · `docs/PRD.md:42-47`
- **Model per teammate:** Claude: 4-step order + allowlist substitution (see §2). OpenCode: per-agent `model: provider/model` (e.g., `anthropic/claude-sonnet-4-5`, `opencode/gpt-5.1-codex`); subagent model falls back to parent's model when not configured; `model` field is per-agent. Crewel: each teammate's model comes from team config (`config.json: lead type + teammate types`), not from a prompt-level pick; any vendor/model combination is allowed. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Specify teammates and models) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Model section) · `docs/PRD.md:55-66`
- **Task board:** Claude: shared task list at `~/.claude/tasks/{team}/` with `TaskCreate/TaskGet/TaskList/TaskUpdate`, file-locked claiming, auto-unblocked dependencies. OpenCode: built-in `task` permission / `todowrite` tool; agents can invoke subagents via `task` tool, but there is no cross-model shared task board — OpenCode's task system is single-vendor and single-session. Crewel: ticket system under `.crewel/teams/{team}/tickets/{id}.json` + Markdown source, with real fields (status/assignee/dependencies/acceptance criteria) and `needs-clarification` as a first-class state that routes to the lead. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Assign and claim tasks; Architecture) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Task permissions, Tools) · `docs/PRD.md:85-101`
- **Messaging / mailbox:** Claude: JSON per-agent inbox at `~/.claude/teams/{team}/inboxes/{agent}.json` + delivery/idle notifications. OpenCode: no cross-agent mailbox; primary→subagent communication is turn-bound (parent→child prompt + child's summary back); navigation via `session_child_*` keybinds and `ListAgents`-style enumeration does not exist. Crewel: per-participant mailbox at `.crewel/teams/{team}/messages/{participant}/` (JSON lines, oldest-first, consumed+archived per turn), watched via `fs.watch` for live push; mid-turn messages queue until turn boundary, interrupt = kill-and-abort. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Architecture: mailbox) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Usage: Navigation between sessions) · `docs/PRD.md:85-101`, `docs/SPEC.md:97-103`
- **Worktree isolation:** Claude: teammates are _not_ worktree-isolated; docs explicitly advise file-set partitioning. OpenCode: worktree isolation is not native; the `serve`/`attach` model assumes a shared working directory. Crewel: mandatory isolation — `crewel/{team}/integration` + per-ticket branches `crewel/{team}/{ticket-id}`, rebase on dependency resolution, conflict → `blocked`. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Avoid file conflicts; Limitations) · [opencode.ai/docs/cli](https://opencode.ai/docs/cli) (`serve`, `run --dir`) · `docs/PRD.md:105-110`
- **Spawning / headless execution:** Claude: `Agent(name=…)` tool in interactive terminal. OpenCode: `opencode run "prompt"` headless invocation (non-interactive mode, `--model provider/model`, `--agent`, `--format json`, `--attach http://localhost:4096` to avoid cold boot), plus `opencode serve` headless server. Crewel translates this to a universal `runTurn(bundle)` adapter contract: `opencode run`, `claude -p`, `codex exec` all implement the same `capabilities()/runTurn()/classifyOutcome()/renderBundle()` shape. [code.claude.com/docs/en/tools-reference](https://code.claude.com/docs/en/tools-reference) (`Agent` tool) · [opencode.ai/docs/cli](https://opencode.ai/docs/cli) (`run`, `serve`, `attach`) · `docs/PRD.md:151-158`
- **TUI / multiplexing:** Claude: native terminal agent panel + optional tmux/iTerm2 split panes (no custom multiplexer). OpenCode: Bubble Tea TUI (`opencode` without args), configurable via `tui.json`, plus `opencode web` browser UI and `opencode attach` for remote backends. Crewel: OpenTUI + `node-pty`/`Bun.spawn` 6-pane layout (lead 58% left focused, teammates grid right), with console fallback on Node 20-24. [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) (Choose a display mode) · [opencode.ai/docs/tui](https://opencode.ai/docs/tui) (TUI, Commands, Attention) · `README.md:90-108`, `docs/PRD.md:162-163`
- **Hooks / lifecycle gates:** Claude: `TeammateIdle`, `TaskCreated`, `TaskCompleted`, `PreToolUse` etc. OpenCode: no direct hook parity, but `permission` (allow/ask/deny + glob patterns), `skill`/`command` templating, and custom tools approximate gating. Crewel adds its own lifecycle operations: heartbeat/stale watchdog, `check-stalls`, rate-limit auto-pause, freeze after 3 failures, `checkCommand` done-gate, interrupt/stop semantics. [code.claude.com/docs/en/hooks](https://code.claude.com/docs/en/hooks) (Hook lifecycle table) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Permissions, Mode) · `docs/PRD.md:136-148`
- **Agent-agnosticism (crewel's gap vs. both vendors):** Neither Claude Teams nor OpenCode's agent system supports heterogeneous vendors on one board by design — Claude docs explicitly state "workers are Claude sessions; to involve a different tool, expose it as MCP" ([code.claude.com/docs/en/agents](https://code.claude.com/docs/en/agents) — bottom note); OpenCode's agents are provider-routed but still host-native (Anthropic/OpenAI/local via one CLI). Crewel's adapter layer is the fix: OpenCode/Claude Code/Codex/mock all speak one ticket/mailbox/worktree protocol, with parity enforced by the senior/principal bar (`needs-clarification`) and structured `TurnReport` validation (`json_schema`/`--output-schema` native where available). `docs/PRD.md:149-159`, `docs/SPEC.md:44-55`, `README.md:16-17`

## 8. Why building this for OpenCode is valuable

This section reports only what first-party sources and the project's own documented rationale support — no invention.

- **OpenCode is the user's daily driver; Claude Teams doesn't run there.** OpenCode is the primary CLI the team actually uses (PRD FR-20: "OpenCode adapter … highest reliability bar, built and tested first" · `SPEC.md:87-90`). Claude Teams lives entirely inside Claude Code and cannot orchestrate OpenCode/Codex teammates. A team built inside OpenCode removes the forced switch to Claude Code just to get coordination. [PRD §5.6](file:docs/PRD.md:149-159) · [agent-teams](https://code.claude.com/docs/en/agent-teams) (Agent teams let you coordinate multiple Claude Code instances)
- **Privacy / local-first / air-gap.** OpenCode is open-source, self-hosted, and provider-agnostic; the operator chooses where prompts and files go. Claude Teams sessions run through Anthropic's infrastructure by design (and Claude Teams storage under `~/.claude/` is local-only and never uploaded only in the narrow sense of the task list — sessions themselves are Claude Code sessions). An OpenCode-native team keeps the coordination layer (` .crewel/`) fully inspectable on disk and lets the operator route sensitive tickets to a local model via OpenCode's provider list. [opencode.ai/docs](https://opencode.ai/docs) (Providers, Config) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Configure) · [agent-teams](https://code.claude.com/docs/en/agent-teams) (Architecture: task list directory persists locally and is never uploaded)
- **Model freedom vs. single-vendor lock-in.** OpenCode lists 75+ providers, including free-tier and local models (Ollama, LM Studio), and lets each agent pin its own `model: provider/id` (`opencode/gpt-5.1-codex`, `anthropic/claude-sonnet-4-5`, etc.). Claude Teams picks each teammate from the Anthropic model family (or allowlist) and fixes it at spawn. An OpenCode-native team can assign a cheap Haiku-class scout to triage, a Sonnet-class builder to implement, and a frontier model only where justified — without leaving the team. [opencode.ai/docs](https://opencode.ai/docs) (Intro) · [opencode.ai/docs/agents](https://opencode.ai/docs/agents) (Model) · [opencode.ai/docs/cli](https://opencode.ai/docs/cli) (`run --model provider/model`) · [agent-teams](https://code.claude.com/docs/en/agent-teams) (Specify teammates and models)
- **True mixed-board parity (the gap no vendor will fill).** Claude docs explicitly narrow heterogeneous work to MCP exposure ("To involve a different tool, expose it to Claude as an MCP server" — [agents](https://code.claude.com/docs/en/agents)). OpenCode's cross-vendor support is still host-native. Crewel is the only target that treats OpenCode, Claude Code, and Codex as equal participants on the _same_ board with the _same_ ticket/mailbox/worktree protocol — a use case neither vendor has an incentive to build. `PRD.md:1-13` · `SPEC.md:23-33` · [agents](https://code.claude.com/docs/en/agents) (Workers are Claude sessions)
- **Better fit for senior-engineer workflow (tickets + inspections).** Claude Teams' shared task list is a flat `pending/in progress/completed` list with optional deps; crewel's ticket model adds assignee, acceptance criteria, and a `needs-clarification` push-back state that is protocol-enforced (every turn validates a `TurnReport`). Worktree-per-teammate plus human-readable state makes `cat`-debuggability a requirement, not an afterthought, which matters when the lead was never supposed to write code. [agent-teams](https://code.claude.com/docs/en/agent-teams) (Assign and claim tasks; Limitations) · `PRD.md:25-30,38-47,85-101`

## 9. Caveats and what not to carry over

- Do not mimic Claude's experimental limitations you can avoid: e.g., add worktree isolation (Claude explicitly does not), make headless/turn-based the default (Claude blocks it), and keep history out of the context bundle (turn state on disk). [agent-teams](https://code.claude.com/docs/en/agent-teams) (Enable: non-interactive; Limitations)
- Do not assume in-memory coordination is available. Claude's own product uses local file storage with file locking — that is the proven pattern; an in-memory bus is a v2 optimization, not a v1 requirement. [agent-teams](https://code.claude.com/docs/en/agent-teams) (Architecture) · [building-c-compiler](https://www.anthropic.com/engineering/building-c-compiler) (Running Claude in parallel: git-based locking history is inspectable)
- Do not quote token-multiplier numbers without the version: the cost page does not publish a single stable multiplier; the docs vary ("significantly more," "roughly proportional to team size"). Cite the source's phrasing, not a derived constant. [costs](https://code.claude.com/docs/en/costs) (Agent team token costs)
